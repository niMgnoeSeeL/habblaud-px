# 휴대폰 점검표

휴대폰 UI를 바꿀 때마다 이 점검표의 모든 항목을 확인한다. 마지막으로 지적받은 항목만 보지 않는다. 항목의 기준은 WCAG 2.2와 Apple HIG에서 가져왔다. 단계별 항목(P1~P3)은 휴대폰 UI 작업의 1~3단계 순서를 따른다.

## 돌리는 법

```
tools/phone/run.sh <OUT> [단계 ...]
```

- **준비:** Habblaud 서버가 `http://localhost:4747`에서 떠 있어야 한다(`npm start`). 다른 주소라면 `HABBLAUD_URL`로 바꾼다.
- **프로필:** 네 프로필을 동시에 찍는다. `PROFILES`로 일부만 고를 수 있다.
  - `iphone-15`: 393×659
  - `iphone-se`: 320×568. WCAG 1.4.10의 320 CSS px 폭이다.
  - `iphone-15-land`: 734×343
  - `iphone-se-land`: 568×320
- **가로 프로필:** 가로 화면이 필요한 단계만 찍는다.
- **결과:** `<OUT>/index.html`에 단계마다 한 줄, 프로필마다 한 칸으로 스크린샷과 요약이 나온다. 자세한 측정값은 `<OUT>/report-<프로필>.json`에 있다.
- **단계 목록:** `python3 tools/phone/shoot.py --list`로 단계 목록과 각 단계가 확인하는 항목을 본다.
- **데모 단계의 재시도:** 데모 모드(`?mock=1`)는 알림이 나오는 때가 실행마다 다르다. 그래서 기다리던 알림이 안 나오면 새 페이지로 두 번 더 시도한다.

## 안전

- **쓰기 요청 차단:** `/api`로 가는 요청 가운데 GET이 아닌 것은 모두 막는다. 그래서 어떤 단계도 실제 세션에 메시지를 보내거나, 권한을 승인·거절하거나, 세션을 시작·종료할 수 없다.
- **화면만 연다:** 단계는 화면을 열기만 하고, 그런 일을 하는 버튼은 누르지 않는다.
- **REAL 단계:** `timelapse`, `deliveries`, `spawn`, `history`는 실제 서버 화면을 휴대폰 포트처럼 연다. `/api/access`는 원격 로그인 상태로 꾸며 답한다. 화면에 실제 세션 내용이 찍히므로 결과 폴더를 밖으로 내보내지 않는다.

## 공통 항목

모든 스크린샷에서 자동으로 측정한다.

1. **C1. 리플로** ([WCAG 2.2 1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)). 320 CSS px 폭에서 가로로 스크롤하지 않고 읽고 쓸 수 있다.
   - 측정: 문서 폭(`sw`)이 화면 폭(`vw`) 이하이다. 넘치면 넘친 요소를 `overflowers`에 적는다.
   - 가로 스크롤 상자 안의 내용은 넘침으로 세지 않는다. 그 상자가 내용에 꼭 필요한지는 사람이 판단한다.
   - 통과: `iphone-se`의 모든 단계가 "리플로 OK"이다.
2. **C2. 타깃 크기** ([WCAG 2.2 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), [Apple HIG](https://developer.apple.com/design/human-interface-guidelines/accessibility)).
   - WCAG 2.5.8은 24×24 CSS px 이상을 요구한다. 작더라도 둘레에 24px 원이 겹치지 않을 만큼 간격이 있으면 예외로 인정한다.
   - Apple HIG는 44×44 pt를 권한다.
   - 측정: 지금 누를 수 있는 컨트롤(화면 안에 있고 다른 요소에 덮이지 않은 것) 가운데 24px 미만(`<24`)과 44px 미만(`<44`)인 것의 수.
   - 통과: `<24`는 0이다. 간격 예외는 스크린샷으로 확인한다. `<44`를 0으로 만드는 일은 P3-2이다.
3. **C3. 방향** ([WCAG 2.2 1.3.4](https://www.w3.org/WAI/WCAG22/Understanding/orientation.html)). 세로와 가로 화면에서 모두 쓸 수 있다.
   - 측정: 가로 프로필의 단계가 모두 성공하고 C1·C2를 통과한다.
4. **C4. 글자 대비** ([WCAG 2.2 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)). 글자는 4.5:1, 큰 글자(24px 이상, 또는 굵은 18.66px 이상)는 3:1이다.
   - 측정(근사치): 글자를 직접 가진 요소마다 글자색과, 조상에서 처음 만나는 불투명한 배경색의 대비를 계산한다. 기준에 못 미친 것을 `contrast.low`에 적는다.
   - 이미지나 그라데이션 위의 글자는 측정하지 않는다. 이런 글자는 스크린샷으로 확인한다.

**보조 측정:**
- **화면 밖 컨트롤(`화면밖`):** 스크롤해서 닿을 수 있으면 괜찮다.
- **가려진 컨트롤(`가려짐`):** 가운데 지점의 맨 위 요소(`elementFromPoint`)가 그 컨트롤이 아닌 것의 수다. 열린 시트 밑에 깔린 컨트롤도 여기에 들어간다.
- **누르기 전 검사:** 도구는 누르려는 자리가 다른 요소에 덮여 있으면 누르지 않고 그 단계를 실패로 남긴다. 다시 시도해서 성공하더라도, 앞선 실패 이유는 `앞선 실패`로 남긴다. 덮인 알림 버튼처럼 그 자체가 발견일 수 있기 때문이다.
- **콘솔 오류(`console`):** 페이지가 낸 오류를 적는다.
- **대비 최솟값:** C4의 최솟값도 함께 적는다.

## 1단계: 명령 기능

5. **P1-1. 권한·질문 카드의 버튼은 화면 아래에 붙은 바에 있다.**
   - 측정: 카드를 연 직후와 카드를 끝까지 스크롤한 뒤 모두 다음을 만족한다.
     - `버튼화면안`이 참이다.
     - 버튼 줄의 버튼이 다른 요소(입력칸 등)에 덮이지 않는다(`버튼가려짐` 0).
     - 버튼 줄의 `position`이 `sticky`나 `fixed`이다(`pos`). 휴대폰에서는 버튼 줄을 상세 시트 맨 아래의 `.ui-perm-bar`로 옮기므로, 그 바의 값을 잰다.
     - 거절 양식이 열려 있으면(`deny-reason`) 그 양식의 버튼 줄(Recusar, Cancelar)을 잰다. 그때는 그 줄이 양식 안에서 아래에 붙는다.
   - 단계: `details-permission`, `approve-buttons`, `details-scrolled`, `question`, `question-options`
6. **P1-2. 카드가 떠 있는 동안에는 메시지 입력칸을 접는다.**
   - 측정: `입력칸`이 거짓이다.
   - 단계: `details-permission`, `question`
7. **P1-3. 거절을 누르면 사유 칸이 보이게 스크롤된다.**
   - 측정: `사유칸화면안`이 참이다.
   - 단계: `deny-reason`
8. **P1-4. 시트는 불투명하다.**
   - 측정: 열린 시트의 배경 알파가 1이다(`반투명` 0).
   - 단계: 모든 단계
9. **P1-5. 토스트가 시트를 덮지 않는다.**
   - 측정: `시트겹침`이 0이다.
   - 단계: `toast-over-sheet`, 그리고 토스트가 보이는 모든 단계
10. **P1-6. 카드 머리는 줄바꿈한다.** 제목과 남은 시간 표시가 한 줄에 다 들어가지 않으면, 글자 묶음을 찌그러뜨리지 않고 다음 줄로 내린다.
    - 측정: `머리넘침`과 `머리겹침`(글자 묶음과 남은 시간 표시의 겹침)이 거짓이다.
    - 측정: `머리글자폭`(머리 폭에서 글자 묶음이 차지하는 비율)이 0.5 이상이다. 0.5는 어림값이고, 판단은 스크린샷으로 한다. 320px 스크린샷에서 단어가 한 글자씩 끊기거나 잘린 글자가 없는지 본다.
    - 단계: `details-permission`, `question`
11. **P1-7. 휴대폰에서는 Enter가 줄바꿈이다.** 보내기는 버튼으로 한다.
    - 측정: 입력칸에 글자를 넣고 Enter를 누른 뒤 값에 줄바꿈이 있다(`Enter줄바꿈`).
    - 단계: `composer-enter`
12. **P1-8. 화면 키보드가 열려도 입력칸과 카드 버튼이 가려지지 않는다**([visualViewport](https://developer.mozilla.org/en-US/docs/Web/API/Visual_Viewport_API) 처리).
    - 자동 측정은 할 수 없다. 헤드리스 WebKit에는 화면 키보드가 없기 때문이다.
    - 확인: 아이폰 실기기에서 휴대폰 접속(`npm run remote:setup`)으로 열고, 입력칸과 사유 칸을 눌러 본다.
13. **P1-9. 가로 화면 규칙 `(max-height: 500px) and (pointer: coarse)`.**
    - 측정: 가로 프로필에서 `가로규칙`이 켜지고, 그 상태에서 P1-1~P1-3과 P1-7이 통과한다.
    - 단계: `details-permission`, `approve-buttons`, `deny-reason`, `question`, `composer-enter`(가로 프로필)

## 2단계

14. **P2-1. 480px 이하에서 타임랩스를 ⋯ 메뉴로 열 수 있다.**
    - ⋯ 메뉴(`ui/moremenu.ts`)는 터치 화면에서만 나온다. 화면 폭 때문에 상단 바에서 빠진 버튼이 메뉴 항목이 된다.
    - 단계: `timelapse`(REAL, 휴대폰 포트처럼). ⋯를 누르고 Timelapse 항목을 눌러 타임랩스가 열리는지 본다.
15. **P2-2. 길게 눌러 순서를 바꾸는 기능을 pointer 이벤트로 만든다**(`ui/touchreorder.ts`: 방, 에이전트, 터미널 탭).
    - 측정: `길게눌러순서바꿈`이 참이다. 사이드바 첫 방의 머리를 길게 누른 뒤 둘째 방 아래로 끌어 놓았을 때 방 순서가 바뀐다.
    - 단계: `reorder`. 터치 pointer 이벤트를 스크립트로 보낸다. 손가락으로 했을 때 스크롤과 제대로 갈리는지는 아이폰 실기기에서 확인한다.
16. **P2-3. 터치 화면에서는 단축키 안내를 숨긴다.**
    - 측정: `단축키안내`의 두 값이 모두 0이다.
      - `표시`: 보이는 단축키 표시(`.ui-kbd`)의 수
      - `글자`: "Enter sends; Shift+Enter adds a new line"이나 "(L)"처럼 글자로 쓴 단축키 안내의 수
    - 단계: 모든 단계, 특히 `help`
    - 버튼 이름(`aria-label`) 안의 "(L)" 같은 표기는 그대로 둔다. 화면에 보이지 않고, 키보드를 붙인 iPad에서는 단축키를 알려 주기 때문이다. ⋯ 메뉴의 항목 이름에서는 뗀다.
17. **P2-4. Web Push 알림.** 알림은 Apple 서버를 거치고, 홈 화면에 추가한 웹앱에서만 동작한다([WebKit](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)).
    - 보내는 것: '당신 차례'(권한 요청, 질문)와 '작업 끝'(에이전트가 턴을 마침). 화면에 뜨는 알림과 같은 문구다(`server/model/office.ts`의 notice).
    - 보내는 때: 맥의 키보드와 마우스 입력이 2분 넘게 없을 때만 보낸다(`ioreg`의 HIDIdleTime). 유휴 시간을 알 수 없는 곳(Docker)에서는 항상 보낸다.
    - 켜는 곳: Configurações › Avisos › Notificações no celular(영어 화면: Settings › Alerts › Phone notifications). 휴대폰 포트로 접속했을 때만 보인다. 알림을 누르면 그 에이전트가 열린다(`?agent=`).
    - 확인(서버): `server/push/*.test.ts`로 본다. RFC 8291 부록 A의 예제 값과 같은 결과가 나오는지, VAPID 서명, 저장(권한 600), 유휴 조건, 410이 오면 구독을 지우는지, 휴대폰 포트에서는 로그인해야만 쓸 수 있는지를 본다.
    - 단계: `settings-phone`(REAL, 휴대폰 포트처럼). 스위치와 안내 문구를 찍는다(`알림스위치`). 헤드리스 WebKit은 홈 화면 앱이 아니어서 '홈 화면에 추가' 안내가 나오는 것이 맞다.
    - 받는 쪽: 홈 화면에 추가한 아이폰 실기기에서, 스위치를 켜고 Mandar um teste(Send a test)로 확인한다.

## 3단계

18. **P3-1. 320px에서 상단 사용량 카드는 가로로 스크롤된다.**
    - 측정: `iphone-se`의 `home`에서 C1을 통과하고 `사용량카드` 값이 다음과 같다.
      - `가로스크롤`이 참이다(카드 줄이 가로로 스크롤된다).
      - `삐져나감`이 0이다(카드 밖으로 나간 글자나 막대가 없다).
    - C1은 화면 폭을 넘는 넘침만 잡는다. 그래서 카드끼리 겹치는 넘침은 `삐져나감`으로 본다.
    - 단계: `home`
19. **P3-2. 터치 영역은 44px이다.**
    - 측정: `<44`가 0이다. 문장 속 링크는 WCAG 2.5.8의 예외이므로 세지 않는다.
    - 휴대폰 터치 화면에서 버튼(`.ui-btn`)과 아이콘 버튼(`.ui-icon-btn`)은 최소 44px이다. 스위치는 iOS 크기(51×31)이고, 누를 수 있는 영역은 높이 44px이다.
    - 예외(WCAG 2.5.8의 24px까지): Codex 카드 안의 '켜기' 버튼, 타임랩스 그래프의 봉우리 표시. 둘 다 44px로 키우면 이웃을 덮는다. 라벨 안의 라디오·체크박스(라벨 줄이 44px)와 문장 안 링크(방 이름 링크처럼 글 사이에 놓인 인라인 버튼 포함)는 세지 않는다.
    - 480px 이하에서는 상단 바에 사이드바, 배달함, 새 에이전트, ⋯만 남긴다. 전체 보기, 내 하루, 세션 기록, 타임랩스, 설정, 도움말은 ⋯ 메뉴로 간다.
    - 단계: 모든 단계. 상단 바 버튼을 누르는 단계는 버튼이 바에 없으면 ⋯를 거친다.
20. **P3-3. 전체 보기(Overview)가 화면 폭에 맞는다.**
    - 확인: 세로와 가로 스크린샷에서 건물 전체가 화면 폭 안에 들어온다.
    - 단계: `overview`
21. **P3-4. 시트는 한 번에 하나만 연다.**
    - 휴대폰 화면에서는 상세 시트를 열면 사이드바와 펼친 피드가 닫힌다. 사이드바나 피드를 열면 나머지 시트가 닫힌다(`client/src/ui/index.ts`).
    - 측정: 열린 시트 수(`시트`)가 1 이하이다. 화면 아래에 접혀 붙은 피드 띠처럼 높이가 화면의 25%가 안 되는 패널은 시트로 세지 않는다.
    - 단계: 모든 단계, 특히 `room-drawer`
22. **P3-5. 탭 줄이 가로로 스크롤되면 그렇다는 신호를 보인다.**
    - 가로로 스크롤되는 줄(터미널 탭, 사용량 카드)은 잘린 쪽 가장자리를 흐리게 한다(`client/src/ui/dom.ts`의 `scrollCue`, `.is-cut-start`, `.is-cut-end`).
    - 측정: 탭 줄(`.ui-ttabs`)이 `scrollers`에 있으면, 스크린샷에서 가장자리 흐림을 확인한다. 이 데모에서는 탭이 둘 이상인 터미널이 나오지 않을 수 있다. 그때는 `home`의 사용량 카드 줄(SE)로 같은 흐림을 확인한다.
    - 단계: `terminal`, `home`

## 범위 밖

PTY 터미널, 캐릭터 편집기, 방 이름 바꾸기, World 창은 설계상 로컬 전용이다. 그래서 단계를 두지 않는다.
